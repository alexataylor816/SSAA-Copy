## RESOLVED this session — both gaps below are fixed, don't re-open them

**`update(...).eq("id", ...)` — FIXED in `backend/src/query/executor.ts`.** The `update` case now calls `rowIdFromFilters(rule, req)` (new helper, sits next to `rowsFrom`) and merges a single-valued `id` filter into each row **before** `rule.canWrite` runs — that ordering matters, because `TASKS.canWrite` looks the project's id up from `row.id`. Only a single-valued `id` filter is honoured; `.eq("id", a).eq("id", b)` and `.in("id", [a,b])` name several rows and are still refused (403), as is any update with no id at all. Row-level scoping still applies to filter-derived ids — there's a test proving a stranger can't hijack a task by naming its id in a filter. The workaround at `web/src/lib/tasks.ts` (`update({ id: taskId, ...changes })`) is gone; it now writes the idiomatic `update(changes).eq("id", taskId)`.

**Availability on behalf of another employee — FIXED in `backend/src/scheduling/service.ts`.** `setAvailability` now takes an optional `employeeId`, resolved by the new `resolveEmployeeToSchedule(user, employeeId)`. The rule, taken from the original's RLS (`Manage availability`, migration `20251213144102`) plus the UI gating in `ProfilesModal.tsx:87-98`:

| target | requirement |
|---|---|
| yourself | always allowed, no permission check (keeps the basic-worker flow alive) |
| someone else on your own roster | `partial` or higher (or admin) |
| someone on a company you're only *connected* to | refused — that is what `schedule_requests` is for; availability must not be a back door |
| unknown id | 404 |
